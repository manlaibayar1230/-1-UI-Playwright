Энэ репозитори нь [saucedemo.com](https://www.saucedemo.com) демо дэлгүүрийн нэвтрэх болон
худалдан авалтын үндсэн урсгалыг Playwright ашиглан автоматжуулсан UI тестүүдийг агуулна.

## Юу хийсэн

- Playwright + TypeScript төсөл `npm init playwright@latest`-ээр үүсгэж тохируулсан.
- `tests/login.spec.ts` файлд 4 тест бичсэн:
  1. Амжилттай нэвтрэх (`standard_user` / `secret_sauce`)
  2. Амжилтгүй нэвтрэх (буруу нууц үг → алдааны мессеж шалгах)
  3. Нэвтэрсний дараах үйлдэл — бараа сагслах (Add to cart → cart badge шалгах)
  4. Гарах (logout) үйлдлээр тестийг зөв төгсгөх
- Бүх тест орчин үеийн locator ашигласан: `getByPlaceholder`, `getByRole`, `getByText`,
  `getByTestId`. XPath огт ашиглаагүй (шалтгааныг код доторх коммент болон доор тайлбарласан).
- `playwright.config.ts` дотор `trace: 'on'` болон `screenshot`/`video` тохиргоог идэвхжүүлсэн
  тул тест ажиллуулах бүрд `trace.zip` болон HTML тайлан үүснэ.
- Codegen (`npx playwright codegen saucedemo.com`) ашиглаж туршиж, гарсан кодыг гараар
  бичсэн тестийн бүтэцтэй харьцуулсан (доор тайлбар).

## Хэрхэн ажиллуулах

```bash
# 1. Хамаарлуудыг суулгах
npm install

# 2. Хөтчүүдийг татаж суулгах (анх удаа л хийнэ)
npx playwright install

# 3. Бүх тестийг ажиллуулах
npx playwright test

# 4. HTML тайланг үзэх
npx playwright show-report

# 5. Trace-тай ажиллуулж, дараа нь trace.zip-ийг нээж үзэх
npx playwright test --trace on
npx playwright show-trace test-results/**/trace.zip
```

## Codegen туршилтын ажиглалт

`npx playwright codegen saucedemo.com` ашиглан хулганаар дарж тест бичүүлэхэд:

- Codegen нь ихэвчлэн `page.locator('#user-name')` шиг ID-аар шүүсэн код гаргадаг бөгөөд
  заримдаа `getByPlaceholder`/`getByRole`-ийг ч ашигладаг, гэхдээ assertion (`expect`)
  автоматаар нэмдэггүй — үүнийг өөрөө гараар нэмэх шаардлагатай.
- Codegen-ийн гаргасан кодыг гараар засварлаж, `data-test` атрибут дээр суурилсан
  `getByTestId`-руу шилжүүлж, утга учиртай `expect` шалгалтуудыг нэмж сайжруулсан.

## Playwright vs Selenium — ажиглалт (README-ийн даалгаварт заасан харьцуулалт)

Хоёулаа Apache 2.0 лицензтэй, үнэ төлбөргүй, нээлттэй эхийн хэрэгслүүд тул сонголт нь
зардлаас бус техникийн ялгаанаас хамаарна. Энэ лабораторийг хийхдээ ажиглагдсан гол
ялгаанууд:

1. Playwright-ийн **auto-wait** механизм нь Selenium-ийг бодвол их цаг хэмнэсэн — элемент
   харагдах хүртэл гараар `WebDriverWait` бичих шаардлагагүй болсон нь код богино,
   тод болгосон.
2. Playwright дээр browser driver тусад нь татаж, PATH тохируулах шаардлагагүй
   (`npx playwright install` нэг команд л хангалттай) байхад Selenium дээр
   ChromeDriver/GeckoDriver-ийн хувилбарыг хөтчийн хувилбартай тохируулах нь урьд нь
   байнга алдаа гаргадаг цэг байсныг сурлагын явцад мэдэрсэн.
3. **Trace viewer** нь алдаа гарсан тестийг DOM snapshot, network, console лог зэрэгтэй
   хамт алхам алхмаар "тоглуулж" харах боломж өгдөг тул дебаг хийхэд Selenium-ийн
   screenshot/log-оос хамаагүй дэлгэрэнгүй бөгөөд хурдан байсан.
4. **Codegen** хэрэгсэл нь тест бичихэд эхлэл болж, шинэхэн хэрэглэгчид Playwright-ийн
   locator-ын синтаксыг хурдан танилцуулж чадсан; Selenium IDE ижил зорилготой ч
   Playwright-ийн орчин үеийн locator (`getByRole` гэх мэт) руу шууд хөрвүүлдэггүй
5. Playwright анхнаасаа хэд хэдэн хөтчийг (Chromium, Firefox, WebKit) нэг API-аар удирддаг
   тул кросс-браузер тест бичихэд тохиргоо бага шаардсан.
6. Selenium-ийн давуу тал нь: илүү удаан хугацаанд хэрэглэгдэж ирсэн тул баримтжуулалт,
   community жишээ илүү өргөн, мөн Java/C#-ыг гол хэрэгсэл болгодог байгууллагуудад илүү
   төлөвшсөн экосистемтэй. Playwright JS/TS-д хамгийн сайн дэмжлэгтэй ч Java/C#/Python
   дээр ч ажилладаг тул хэл сонголтын хувьд аль аль нь уян хатан.
7. Ерөнхийд нь: шинэ төсөлд илүү хурдан, тогтвортой (flaky биш) тест бичихэд Playwright
   давуу байгаа мэт мэдрэгдсэн ч, аль хэдийн Selenium дээр суурилсан том хуучин төсөлд
   шилжих зардал өндөр байх нь ойлгомжтой.

## Locator сонголтын тухай (XPath-аас зайлсхийсэн шалтгаан)

`getByRole`, `getByPlaceholder`, `getByText`, `getByTestId` зэргийг ашигласан бөгөөд
XPath ашиглаагүй, учир нь:

- XPath (`//div[3]/ul/li[2]/a` гэх мэт) нь HTML-ийн дотоод бүтцээс хэт хамааралтай тул
  дизайн бага зэрэг өөрчлөгдмөгц (нэг `div` нэмэгдэхэд ч) тест хугарах магадлалтай — маш
  **эмзэг (fragile)** тест үүсгэдэг.
- `getByRole` зэрэг нь хэрэглэгч (мөн screen reader) хуудсыг хэрхэн "хардаг"-тай ижил
  логикоор ажилладаг тул илүү тогтвортой бөгөөд нэгэн зэрэг **accessibility**-г шалгаж өгдөг.
- `getByTestId` нь хөгжүүлэгчийн зориуд өгсөн тогтвортой `data-test` атрибут дээр
  суурилдаг тул визуал дизайн өөрчлөгдсөн ч эвдрэхгүй.
- Код унших, засварлахад ч `getByRole('button', { name: 'Login' })` нь XPath-аас
  хамаагүй ойлгомжтой.

## Test isolation

Playwright тест бүрд шинэ, цэвэр browser context (хоосон cookie/localStorage) өгдөг
тул `beforeEach`-д зөвхөн нийтлэг "хуудас руу орох" алхмыг л тавьсан. Тест бүр
бие даан, дараалалгүйгээр ажиллах боломжтой (`fullyParallel: true`).

Эхлээд "saucedemo сайт өөрчлөгдчихсөн юм болов уу" гэж бодсон. Гэхдээ screenshot дээр
элемент (жишээ нь сагсны badge "1") **бодитоор харагдаж байсан** — зүгээр л Playwright
олж чадаагүй байв. Энэ нь миний locator-ийн логик буруу гэдгийг харуулж байлаа.

**Шалтгаан:** Playwright-ийн `getByTestId()` анхдагчаар `data-testid` гэсэн HTML
атрибутыг хайдаг. Харин saucedemo.com сайт `data-test` (зурлагагүй, өөр нэртэй)
атрибут ашигладаг байв. Энэ жижиг ялгаа болохоор `getByTestId()` юу ч олохгүй
байсан юм.

**Шийдэл:** `playwright.config.ts` дотор дараах мөрийг нэмэв:

```typescript
use: {
  testIdAttribute: 'data-test',
}
```

Үүний дараа бүх 4 тест PASS

**Сурсан зүйл:** Locator бичихээсээ өмнө хуудасны бодит HTML-ийг (Chrome DevTools →
Inspect) шалгаж, атрибутын нэрийг таамаглах бус баталгаажуулж бичих нь чухал юм байна.
Ялангуяа `data-test` vs `data-testid` шиг ойролцоо нэртэй атрибутуудыг андуурахад
хялбар байдаг талыг өөрийн биеэр мэдэрлээ.
